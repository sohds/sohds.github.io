01 / 현업에서 배운 것

접근할 수 있는 도구로,
실제 업무에 닿는 변화를.

산업은행 인턴으로 경험한 사내 업무 혁신은
제가 이 팀에 관심을 갖게 된 출발점입니다.

한국산업은행 · AI디지털전략부 인턴 · 2026.06—08

여신승인신청서 종합의견 작성 보조

System Prompt / Domain / Feedback
제가 맡은 일

기존 서비스 소스코드와 개발 서버에 접근할 권한이 없었습니다. 대신 업무 보조 아이디어를 시스템 프롬프트로 설계하고 KDB GPT WebUI에서 직접 실행하며 동작을 확인했습니다.

사용자마다 다른 판단 기준

여신 교재 6권과 신청서를 분석해 영업 담당자와 심사역의 관점을 구분했습니다. 지점 실무진의 검토를 받아 작성 지침과 현장 관행의 차이를 보완했습니다.

제안이 실제 기능이 되기까지

  1. 업무 문서에서 과제를 발견하고 기능 제안
  2. 역할별 시스템 프롬프트 설계와 WebUI 실행
  3. 현업 검토를 반영한 개선
  4. 회장 보고의 팀 사례 · KDB GPT 정식 배포

제 기여는 제안·프롬프트 설계·실행 및 검토입니다. 서비스 코드 반영과 배포는 담당자들이 진행했습니다.

의도를 처리하는 API부터 동료가 검토할 화면까지.
문제에 필요한 구성 요소를 직접 연결했습니다.

정보경영연구실 · 산학 과제 · 2024.04—10

AI Sales Assistant

고객의 실시간 쇼핑 상태를 반영하는 가상 휴먼 대화 엔진 개발. QA와 추천 모듈, 통합 API를 맡았습니다.

가격 질문에 환불 규정이 나왔을 때

NLU의 의도 분류와 개체 추출 개념으로 질문을 구조화했습니다. 추출 결과를 의도에 맞는 모듈로 전달하고 FastAPI로 통합했습니다.

질문 → Intent + Entity(JSON)
→ QA / Casual Talk / Recommend → 답변
+30%pQA 파이프라인 개선 전후 정답률

직접 작성한 100문항을 연구실 구성원 5명이 정오로 판정한 정성평가. 개별 라우팅 단계만의 효과나 외부 벤치마크 점수는 아닙니다.

구현 범위와 배운 점 보기
  • LLM API로 의도와 질문 키워드인 Entity 추출
  • QA·추천 모듈 및 전체 통합 API 담당
  • 질문의 의미를 후속 모듈이 사용할 정보로 표현하는 설계의 중요성 확인
  • 지식 그래프 구축은 다른 팀원의 담당
미래에셋증권 AI Festival · 3인 팀 · 2026.08—09

연금 AI Agent

제공 문서를 근거로 연금 제도와 세제 질문에 답하는 서비스. 금융 분야 팀원 2명과 함께하며 기술 설계와 구현을 총괄했습니다.

동료도 품질을 확인할 수 있도록

원문과 검색 청크를 대조하는 검수 도구를 만들었습니다. 검색 구성과 문서 분할을 비교하고 실제 요청 경로까지 점검했습니다.

문서 → 파싱·청킹 → Hybrid RAG
→ 근거가 있는 답변 → 검수·평가
93.8%내부 평가 419문항 · 근거 문서 Hit@5

검색 상위 5개 청크 중 정답 근거 문서에 속하는 청크가 포함된 비율입니다. 해당 청크에 정답 문장 전체가 포함됐다는 뜻은 아닙니다. 답변 정답률이나 공식 심사 점수가 아닙니다.

검증과 서비스 구현 보기
  • BM25와 벡터 검색을 RRF로 결합
  • 비개발 팀원이 원문과 청크를 검토할 수 있는 도구 구현
  • 실제 API 경로로 459건 실행, 형식 누락과 요청 실패 점검
  • Docker·Nginx·NCP 기반 서버 배포
03 / 지금의 관심

LLM과 함께 쌓은 지식은
어떻게 다시 쓰일 수 있을까?

취업 준비에서는 지침과 경험을 로컬 파일로 관리해 LLM과의 작업에 재사용했습니다. 산업은행 인턴 중에는 규정 Wiki 구축 PoC에서 주어진 지침과 스키마로 모델별 산출물과 엔티티 구성 방식을 비교하고, 개정 처리와 스키마의 개선점을 기록했습니다.

원본을 읽고, 연결하고, 다시 찾아 쓰는 구조

저장소의 지침과 스키마를 바탕으로 재구성한 개념도입니다. 실제 규정 내용과 내부 식별자는 포함하지 않았습니다.

A / INGEST WORKFLOW
01 INPUT
원본 확인문서 식별 · 시행 기간 · 상태
02 EXTRACT
규칙과 예외 추출의미 단위로 분리

관련 문서 상호 연결
04 RECORD
색인·이력 갱신처리 기록 작성
원본 보관
별도 Lint 절차 · 출처 누락 / 끊어진 링크 / 고립된 페이지 / 규칙 누락 및 충돌 점검

LLM이 지침을 따라 파일을 처리하는 흐름을 요약했습니다. 단계별 독립 에이전트나 자동 검사 파이프라인이 모두 구현됐다는 의미는 아닙니다.

주장 하나에서 근거까지 되짚기
Wiki의 주장 → 출처 문서 식별자 → 원문의 제목 경로 → 시작·종료 줄
각 주장의 근거 위치를 남기도록 스키마에서 요구하는 구조입니다. 실험에서는 실제 산출물이 이 기준을 지키는지도 확인했습니다.

화살표는 문서 간 근거·참조 관계를 나타냅니다. ‘원본 A/B’와 페이지 배치는 설명용이며 실제 문서명이나 연결 개수를 재현하지 않았습니다.

C / QUERY WORKFLOW
사용자 질문→Wiki 색인→관련 페이지→근거를 표시한 답변

필요하면 보관 원본을 확인하고, 불확실한 내용은 불확실하다고 답하도록 지침을 두었습니다.

QUESTION

같은 원본을 주면,
같은 수준의 Wiki가 만들어질까?

동일한 규정 샘플로 모델별 ingest 산출물을 비교했습니다. 필수 섹션의 누락, 깨진 링크, 원본에 없는 내용 생성을 확인했습니다.

발견 → 형식과 원본 충실성도 품질이다

내용이 그럴듯해 보여도 필수 섹션이 빠지거나 연결이 깨질 수 있었습니다. 원본을 옮기지 않는 동작에서는 지시문의 ‘이동’과 ‘수정’ 구분이 모호했던 점도 확인했습니다.

모델 선택과 함께, 지시문과 산출물의 검증 기준을 살펴봐야 했습니다.

QUESTION

개정 문서를 넣으면
기존 지식은 어떻게 바뀔까?

같은 문서 ID를 가진 개정판을 넣었습니다. 개정 여부를 명시하지 않았을 때는 충돌로 처리됐고, 개정판임을 밝힌 뒤에는 연결된 엔티티 갱신을 관찰했습니다.

발견 → 갱신 성공과 이력 보존은 다르다

과거 규칙의 ID가 새 내용에 재사용되고, 삭제된 예외가 별도의 이력 없이 사라지는 문제를 발견했습니다.

이 문제는 실험 기록에 남겼으며, 해결을 완료했다고 주장하지 않습니다.

QUESTION

직급별로 모을까,
업무별로 나눌까?

직급 중심과 업무 중심의 엔티티 구성을 비교하고, 여신·수신·기획·인사·예산의 5개 영역을 누적해 파일 구성이 어떻게 변하는지 살폈습니다.

발견 → 업무별 구성에도 조건이 필요하다

여러 영역의 규칙이 한 직급 파일에 쌓였습니다. 하지만 업무별 구성에서도 하위 항목을 한데 묶으면 파일이 커졌습니다.

‘업무별이 더 낫다’는 결론은 항목을 나누는 경계를 명확히 할 때 유지됐습니다. 파일 크기를 검색 성능으로 해석하지는 않았습니다.

표의 모양에서 규칙의 관계로

중첩 표의 조건과 전결권자를 규칙별로 묶고 비고를 적용 대상 아래에 배치했습니다. 복잡한 관계를 Markdown 계층으로 표현하는 방식이 새로웠습니다.

지금 이어가고 싶은 방향

반복 설명을 줄이는 편리함에서 출발해, LLM과 함께 축적한 지식을 나누고 갱신하며 재사용하는 Wiki로 발전시키고 싶습니다.

인턴 개인 PoC 및 비교 실험입니다. 운영 서비스 반영, 검색 성능 향상, 토큰·비용 절감을 입증한 결과는 아닙니다. 로컬 파일 기반 작업과 로컬 모델 실행은 구분합니다.

다음으로 하고 싶은 일

사내 업무의 변화가
제품이 되는 곳에서.

산업은행에서 제가 제안한 기능이 실제 서비스에 반영되며, 구성원의 일을 돕는 데서 보람을 느꼈습니다. 코드에 직접 접근하지 못했던 아쉬움은 업무 이해에서 구현과 개선까지 맡고 싶다는 의지로 이어졌습니다.

당근에서는 구성원의 맥락을 이해하고, 필요한 기능과 도구를 연결하며, 함께 쓰는 AI 제품의 품질을 확인하는 일에 기여하고 싶습니다.
