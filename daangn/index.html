과제와 내 역할

규정의 조건·예외·출처를 보존하면서 갱신하고 재사용할 수 있는 구성을 검토했습니다. 주어진 지침과 스키마를 기반으로 모델별 변환 결과와 직급·업무별 문서 구성을 비교했습니다.

QUESTION

같은 원본을 주면,
같은 수준의 Wiki가 만들어질까?

동일한 규정 샘플로 모델별 ingest 산출물을 비교했습니다. 필수 섹션의 누락, 깨진 링크, 원본에 없는 내용 생성을 확인했습니다.

발견 → 형식과 원본 충실성도 품질이다

내용이 그럴듯해 보여도 필수 섹션이 빠지거나 연결이 깨질 수 있었습니다. 원본을 옮기지 않는 동작에서는 지시문의 ‘이동’과 ‘수정’ 구분이 모호했던 점도 확인했습니다.

모델 선택과 함께, 지시문과 산출물의 검증 기준을 살펴봐야 했습니다.

QUESTION

개정 문서를 넣으면
기존 지식은 어떻게 바뀔까?

같은 문서 ID를 가진 개정판을 넣었습니다. 개정 여부를 명시하지 않았을 때는 충돌로 처리됐고, 개정판임을 밝힌 뒤에는 연결된 엔티티 갱신을 관찰했습니다.

발견 → 갱신 성공과 이력 보존은 다르다

과거 규칙의 ID가 새 내용에 재사용되고, 삭제된 예외가 별도의 이력 없이 사라지는 문제를 발견했습니다.

이 문제는 실험 기록에 남겼으며, 해결을 완료했다고 주장하지 않습니다.

QUESTION

직급별로 모을까,
업무별로 나눌까?

직급 중심과 업무 중심의 엔티티 구성을 비교하고, 여신·수신·기획·인사·예산의 5개 영역을 누적해 파일 구성이 어떻게 변하는지 살폈습니다.

발견 → 업무별 구성에도 조건이 필요하다

여러 영역의 규칙이 한 직급 파일에 쌓였습니다. 하지만 업무별 구성에서도 하위 항목을 한데 묶으면 파일이 커졌습니다.

‘업무별이 더 낫다’는 결론은 항목을 나누는 경계를 명확히 할 때 유지됐습니다. 파일 크기를 검색 성능으로 해석하지는 않았습니다.

원본을 읽고, 연결하고, 다시 찾아 쓰는 구조

저장소의 지침과 스키마를 바탕으로 재구성한 개념도입니다. 실제 규정 내용과 내부 식별자는 포함하지 않았습니다.

원문과 검색 청크를 대조하는 검수 도구를 만들었습니다. 검색 구성과 문서 분할을 비교하고 실제 요청 경로까지 점검했습니다.

문서 → 파싱·청킹 → Hybrid RAG
→ 근거가 있는 답변 → 검수·평가
93.8%내부 평가 419문항 · 근거 문서 Hit@5

검색 상위 5개 청크 중 정답 근거 문서에 속하는 청크가 포함된 비율입니다. 해당 청크에 정답 문장 전체가 포함됐다는 뜻은 아닙니다. 답변 정답률이나 공식 심사 점수가 아닙니다.

청킹·답변 검증·배포 과정 보기

모델은 경계를 고르고, 코드는 원문을 자릅니다

LLM이 원문을 다시 쓰는 대신 분할 경계를 선택하게 하고, 코드가 해당 원문 구간을 잘라 청크를 만들었습니다. 58개 문서를 358개 청크로 구성하고, 금융 분야 팀원이 원문과 청크를 대조할 수 있는 검수 도구를 구현했습니다.

검색 결과와 계산 결과를 답변 근거로 연결

BM25·벡터 검색을 RRF로 결합했습니다. 숫자 답변은 계산 결과와 대조하고, 계산 결과도 근거로 제공하도록 구성했습니다. 답변의 출처와 형식 누락을 점검하며 실제 API 경로로 총 459건을 실행했습니다.

배포 후 다시 시작되는 것까지 확인

Docker·Nginx·NCP Ubuntu 환경에 배포하고 프로세스 재시작과 서버 재부팅 이후의 복구를 점검했습니다.

459건은 내부 질문 438건과 상품 관련 회귀 점검 21건의 합계입니다. 개선 과정에서 수행한 실행 기록으로, 최종 버전 전체의 통과율을 의미하지 않습니다.

4인 산학 과제에서 이미지 생성 트랙을 맡았습니다. VLM으로 의류의 패턴과 주름 정보를 추출하고, 패턴을 반영한 캡션과 여러 시점의 프롬프트를 구성했습니다.

Runway Gen-4의 생성 결과를 LLM 평가 기준과 SSIM·LPIPS·CLIPScore로 살펴보고, 평가 피드백을 프롬프트 수정과 재생성에 연결했습니다.

생성 결과를 평가하고 다시 시도하는 흐름을 실험했습니다. 품질 개선율을 수치로 입증한 결과는 아닙니다.
