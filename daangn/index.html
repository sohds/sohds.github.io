02 / My ongoing question

LLM과 함께 쌓은 지식은
어떻게 다시 쓰일 수 있을까?

취업 준비의 지침과 경험을 매번 설명하는 대신, 로컬 파일로 관리해 LLM과의 작업에 재사용했습니다. 이 관심을 전결권 규정 Wiki 실험으로 넓히며 모델의 결과뿐 아니라 지식을 나누고 갱신하는 기준을 살폈습니다.

원본을 읽고, 연결하고, 다시 찾아 쓰는 구조

저장소의 지침과 스키마를 바탕으로 재구성한 개념도입니다. 실제 규정 내용과 내부 식별자는 포함하지 않았습니다.

LLM이 지침을 따라 파일을 처리하는 흐름을 요약했습니다. 단계별 독립 에이전트나 자동 검사 파이프라인이 모두 구현됐다는 의미는 아닙니다.

화살표는 문서 간 근거·참조 관계를 나타냅니다. ‘원본 A/B’와 페이지 배치는 설명용이며 실제 문서명이나 연결 개수를 재현하지 않았습니다.

필요하면 보관 원본을 확인하고, 불확실한 내용은 불확실하다고 답하도록 지침을 두었습니다.

QUESTION

같은 원본을 주면,
같은 수준의 Wiki가 만들어질까?

동일한 규정 샘플로 모델별 ingest 산출물을 비교했습니다. 필수 섹션의 누락, 깨진 링크, 원본에 없는 내용 생성을 확인했습니다.

발견 → 형식과 원본 충실성도 품질이다

내용이 그럴듯해 보여도 필수 섹션이 빠지거나 연결이 깨질 수 있었습니다. 원본을 옮기지 않는 동작에서는 지시문의 ‘이동’과 ‘수정’ 구분이 모호했던 점도 확인했습니다.

모델 선택과 함께, 지시문과 산출물의 검증 기준을 살펴봐야 했습니다.

QUESTION

개정 문서를 넣으면
기존 지식은 어떻게 바뀔까?

같은 문서 ID를 가진 개정판을 넣었습니다. 개정 여부를 명시하지 않았을 때는 충돌로 처리됐고, 개정판임을 밝힌 뒤에는 연결된 엔티티 갱신을 관찰했습니다.

발견 → 갱신 성공과 이력 보존은 다르다

과거 규칙의 ID가 새 내용에 재사용되고, 삭제된 예외가 별도의 이력 없이 사라지는 문제를 발견했습니다.

이 문제는 실험 기록에 남겼으며, 해결을 완료했다고 주장하지 않습니다.

QUESTION

직급별로 모을까,
업무별로 나눌까?

직급 중심과 업무 중심의 엔티티 구성을 비교하고, 여신·수신·기획·인사·예산의 5개 영역을 누적해 파일 구성이 어떻게 변하는지 살폈습니다.

발견 → 업무별 구성에도 조건이 필요하다

여러 영역의 규칙이 한 직급 파일에 쌓였습니다. 하지만 업무별 구성에서도 하위 항목을 한데 묶으면 파일이 커졌습니다.

‘업무별이 더 낫다’는 결론은 항목을 나누는 경계를 명확히 할 때 유지됐습니다. 파일 크기를 검색 성능으로 해석하지는 않았습니다.

표의 모양에서 규칙의 관계로

중첩 표의 조건과 전결권자를 규칙별로 묶고 비고를 적용 대상 아래에 배치했습니다. 복잡한 관계를 Markdown 계층으로 표현하는 방식이 새로웠습니다.

지금 이어가고 싶은 방향

반복 설명을 줄이는 편리함에서 출발해, LLM과 함께 축적한 지식을 나누고 갱신하며 재사용하는 Wiki로 발전시키고 싶습니다.

인턴 개인 PoC 및 비교 실험입니다. 운영 서비스 반영, 검색 성능 향상, 토큰·비용 절감을 입증한 결과는 아닙니다. 로컬 파일 기반 작업과 로컬 모델 실행은 구분합니다.
